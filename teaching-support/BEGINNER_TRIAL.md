# Sessions 1–3: trial with 2–3 Java beginners

**Status: prepared; no learner trial results yet.** The protocol is also inside the HTML at `#beginner-trial`. Technical verification and actual learner observation are separate evidence.

## Before the first meeting

1. Choose 2–3 students with no prior Java study. Use learner labels L1, L2, L3 in records.
2. Give each a writable personal project copy and separate H2 file. Check its printed absolute filename. Use fictional exercise names; do not share databases or solutions.
3. Follow the HTML schedule at `#practice-schedule`, splitting meetings into 45–60-minute periods. Prepare JDK/Maven/dependencies before assessing application skills; record setup time separately.
4. Let each learner read and practise the relevant lesson before the checkpoint. During independent cards close completed examples and AI tools. Allow their notes, compiler errors, published WSDL/XSD, supplied setup configuration and ordinary wsimport generation.
5. Use `LEARNER_CARDS.md` for requirements. Use one row per learner/card in `observations.csv`, with an additional row for each retest or next-day check. Never fill observations from assumptions or successful model-generated code.

## Observation method

Ask the learner to predict before running, name the input and output, and explain their first error clue. Observe the actual commands, code, tests and explanation.

Record the exact sentence or missing step that caused confusion. Do not immediately write the solution. After about 10 minutes stuck, give a small pointer if needed and record its exact wording. Card times are observation windows, not speed grades; learners can continue after the window.

Use these outcomes consistently:

| Outcome | Evidence | Follow-up |
|---|---|---|
| Independent | Writes, tests and explains the new behaviour using permitted references, without an instructor hint or code | New variation and next-day recall |
| Small hint needed | Continues after a pointer to a term, file, error or test | Record hint; fresh retest without it |
| Guided example needed | Requires a demonstrated step or substantial application code | Smaller guided example, then new independent variation |
| Environment blocked | Setup, network, folder or port prevents attempting the skill | Resolve separately; rerun the learning task |

## Revise the lesson from findings

If two learners stumble on the same instruction, treat it as a likely teaching gap. A difficulty affecting one learner still deserves review of the wording and prerequisite.

For each gap, quote the problematic instruction, identify the missing concept or action, add a small explanation/example/expected output in the matching HTML section, and give changed task values on retest. Do not call the gap fixed merely because a student copied the original reference successfully.

Use `FINDINGS_TEMPLATE.md` to record before/after findings and remaining gaps. A learner is ready only for independently demonstrated skills that survive next-day recall. Two or three learners provide an initial usability check, not a guarantee for every future class.

## Completion evidence

- All participants attempted the relevant cards after learning their prerequisites.
- Application behaviour, failures and explanations were observed, not inferred from quiz scores.
- Hints and environment blocks were recorded separately.
- Repeated confusing steps were revised and retested using new variations.
- Next-day recall was observed and outstanding gaps were recorded.

Return anonymous observations and exact confusing phrases for the next HTML revision. Keep identifiable student information in your normal school records rather than this trial sheet.
